# Repository Guidelines

## Project Structure & Module Organization

This is a ROS 2 Humble workspace for the DDDMR global planner subset. Source packages live under `src/`:

- `src/dddmr_sys_core`: shared actions, services, enums, and core interfaces.
- `src/dddmr_perception_3d`: perception layers, graph data, plugins, maps, configs, launch files, and RViz views.
- `src/dddmr_global_planner`: global planner libraries, node executable, scripts, launch/config files, RViz views, sample data, and `test/dummy_pc_pub.cpp`.

Workspace-local `build/`, `install/`, and `log/` directories are generated by colcon and should not be treated as source.

## Build, Test, and Development Commands

Run commands from the workspace root:

```bash
source /opt/ros/humble/setup.bash
colcon build --symlink-install --packages-up-to global_planner --cmake-args -DCMAKE_BUILD_TYPE=Release
source install/setup.bash
```

The build command compiles `dddmr_sys_core`, `perception_3d`, and `global_planner` without the excluded full navigation stack dependencies such as GTSAM.

Useful local smoke checks:

```bash
ros2 run global_planner occupancy2ground --ros-args -p map_dir:=src/dddmr_global_planner/data/warehouse.pgm
ros2 run global_planner global_planner_node --ros-args --params-file src/dddmr_global_planner/config/path_planning_on_2d_static_layer.yaml
```

## Coding Style & Naming Conventions

C++ targets use C++17 with `CMAKE_CXX_EXTENSIONS OFF`. Match the existing ROS 2 style: two-space indentation inside functions, snake_case file names, PascalCase classes, and trailing underscores for member variables where already used. Keep package names and exported targets consistent with `package.xml` and `CMakeLists.txt` (`global_planner`, `perception_3d`, `dddmr_sys_core`). Python scripts in `script/` should remain executable ROS 2 entry points.

## Testing Guidelines

No formal unit test suite is currently defined. Treat a clean colcon build as the minimum validation. For planner or perception behavior changes, add focused tests or small executable checks near the affected package before broadening scope. Run package-level checks when available:

```bash
colcon test --packages-select global_planner
colcon test-result --verbose
```

## Commit & Pull Request Guidelines

The current history uses concise Conventional Commit-style messages, for example `chore: manage dddmr global planner working space`. Prefer `type: summary` with a clear lower-case type such as `fix`, `feat`, `chore`, or `docs`.

Pull requests should describe the affected package, the behavior or interface change, and the exact build/test commands run. Link related issues when available. Include RViz screenshots or bag/demo notes for user-visible planning or perception changes.

## Security & Configuration Tips

Do not commit secrets, machine-specific paths beyond documented examples, or generated colcon artifacts. Keep demo maps, YAML configs, launch files, and RViz files in their package-specific directories so installed layouts remain predictable.
